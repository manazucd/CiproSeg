CiproSeg

A PyTorch framework for binary cell segmentation with Leave-One-Series-Out cross-validation

v0.1.0 - Stable
⬢ Python 3.9+ ◈ PyTorch 2.2+ ⚖ Apache-2.0 ⊞ Single GPU

CiproSeg trains a U-Net on time-series microscopy data, holding out one experimental series at a time for testing. Each fold gets its own checkpoint, validation curves, and test metrics. At the end you have a per-fold breakdown of segmentation performance across the entire dataset with no data leakage, deterministic seeds, and a single config file controlling the whole run.

The framework was built for E. coli fluorescence microscopy experiments involving ciprofloxacin-treated and control populations, though it works with any binary segmentation task that follows the expected directory structure.

Installation

Clone the repository and install in editable mode:

git clone https://github.com/manazucd/CiproSeg.git
cd CiproSeg
pip install -e .

For development (adds pytest, ruff, mypy):

pip install -e ".[dev]"

For the optional browser-based GUI (fastapi, uvicorn):

pip install -e ".[gui]"

If your TIFF files use LZW or similar compression, you will also need:

pip install imagecodecs

Verify that the CLI entry points are working:

ciproseg-train --help
ciproseg-eval  --help
ciproseg-infer --help
ciproseg-gui   --help
ℹ️ Requirements
Python 3.9 or newer and PyTorch 2.2 or newer. A CUDA GPU is recommended for training but not required. The full dependency list is in requirements.txt.

Quick Start

Once installed, a complete training run takes three steps:

1

Organise your data

Place images and masks into matched directory trees with one subfolder per experimental series. See Dataset Layout for the full specification.

2

Edit the config

Open configs/experiment.yaml and set dataset.root to the path of your data folder. Adjust model.name, patch size, epochs, and other parameters as needed.

3

Run training

Launch the LOSO training loop. The framework handles fold construction, checkpointing, validation, and test evaluation automatically.

ciproseg-train --config configs/experiment.yaml

When training completes, results are written to a timestamped directory under runs/. Each fold gets its own checkpoint, training curves, and test metrics.

You can also run training from Python directly:

from ciproseg.utils.config import load_config
from ciproseg.core.engine import Engine

cfg = load_config("configs/experiment.yaml")
Engine(cfg).fit()

Dataset Layout

CiproSeg expects images and masks in matched directory trees. Each subdirectory under images/ and masks/ represents one experimental series. One series is held out per LOSO fold.

your_data/ images/ series_A/ frame_000.tif frame_001.tif ... series_B/ ... masks/ series_A/ frame_000.tif frame_001.tif ... series_B/ ...

Filenames must match exactly between images/<series>/ and masks/<series>/. The build step will raise an error if there is any mismatch. Supported formats are .tif, .tiff, .png, .jpg, and .jpeg.

Masks should be binary: any nonzero pixel is treated as foreground. Internally, the framework reads masks with a threshold of 128, so values of 255 for foreground and 0 for background work well.

You can verify that your dataset is correctly paired by running the included check tool:

python tools/check_dataset_pairs.py /path/to/your_data

Training

ciproseg-train --config configs/experiment.yaml

This builds a LOSO cross-validation loop: for N series, N folds run sequentially. In each fold, one complete series is held out as the test series. Frames from the remaining series are split by temporal order into training and validation subsets according to dataset.train_frac (for example, 0.8 gives an 80/20 train/validation split).

Validation during training

Validation is performed periodically during training (every 10 epochs, with the final epoch also validated). The probability map is binarised using validation.checkpoint_threshold -- normally 0.5 -- and the validation metrics are computed. The checkpoint with the highest validation Dice is saved as best.pt. This threshold is used for checkpoint selection; it is not necessarily the final threshold used for test evaluation or inference.

Threshold selection after training

After training a fold, CiproSeg reloads that fold's best.pt and performs a threshold sweep on the validation set only. Each value listed in validation.sweeping_thresholds is applied to the same validation probability maps. Dice, IoU, precision, and recall are averaged across validation frames, and the threshold with the highest mean validation Dice is selected.

Validation selects the threshold
The held-out test series is never used to choose the threshold. Once the validation-selected threshold is fixed, it is applied once to the held-out test series to report final test metrics.

You can override the seed or force CPU mode from the command line:

ciproseg-train --config configs/experiment.yaml --seed 42
ciproseg-train --config configs/experiment.yaml --cpu

Output structure

Each run creates a unique timestamped directory. Nothing is ever overwritten.

runs/<config>/<model>/<timestamp>/ config_resolved.yaml train.log run_summary.pt run_summary.json fold_01_test_seriesA/ best.pt best.json last.pt last.json loss.png dice.png fold_02_test_seriesB/ ...

config_resolved.yaml records the configuration used for the run. train.log captures epoch losses, validation metrics, and fold summaries. Each fold directory contains the best and latest checkpoints, JSON sidecars with checkpoint metadata, and training curves. The top-level run_summary.json is the easiest file to inspect when choosing the correct fold-specific threshold for later evaluation or inference.

Checkpoint contents

Every .pt file is a dictionary with the following keys:

Key Description
model Model state dict (weights and buffers)
optim Optimizer state dict
sched Scheduler state dict (or None)
cfg Full experiment config used for the run
fold_name Fold identifier, e.g. fold_01_test_seriesA
fold_id Numeric fold index
best_val_metric Best validation Dice observed during training
epoch Epoch at which checkpoint was saved

The JSON sidecar files (best.json, last.json) store the same metadata minus the large tensors, so you can browse results without calling torch.load.

Run Summary JSON

At the end of a LOSO run, CiproSeg writes run_summary.json. The file can be large because it stores fold-level test metrics and the complete validation threshold sweep, but only a few fields are needed for most day-to-day use.

Most important fields

Field Meaning
best_validation_thresholds Compact per-fold lookup table containing fold_id, the corresponding held_out_series, and the validation-selected threshold. This is the quickest place to look before inference.
best_validation_dice_across_folds The highest checkpoint-selection validation Dice recorded across the folds. It is a validation quantity, not a test-set score.
mean_test_metrics_across_folds Mean final held-out test metrics across all LOSO folds.
fold_results Detailed record for every fold, including the best checkpoint epoch, threshold selection record, and final test metrics.
threshold_selection.selected_threshold The threshold selected from that fold's validation set by maximising mean validation Dice.
threshold_selection.metrics_by_threshold Validation Dice, IoU, precision, and recall for every candidate threshold that was swept.
test_metrics Final metrics on the fold's held-out test series after applying the already selected validation threshold.

Selecting the threshold for inference

The checkpoint and threshold must come from the same fold. First identify which fold's best.pt you want to use. Then look up that fold in best_validation_thresholds and copy its threshold value.

# Example: run_summary.json says fold 1 / seriesA uses threshold 0.45
ciproseg-infer \
  --ckpt runs/.../fold_01_test_seriesA/best.pt \
  --input path/to/images/ \
  --output predictions/ \
  --threshold 0.45

Do not automatically use 0.5 for inference merely because validation.checkpoint_threshold is 0.5. The checkpoint threshold is used during periodic validation for checkpoint selection. When threshold sweeping is enabled, the fold-specific selected_threshold is the threshold intended for final binarisation.

Evaluation

Point ciproseg-eval at a checkpoint. The checkpoint stores the model and fold metadata. To reproduce the final fold evaluation, also pass the validation-selected threshold recorded for that fold in run_summary.json:

ciproseg-eval   --ckpt runs/.../fold_01_test_seriesA/best.pt   --thr 0.45

The evaluator loads the model architecture from the saved config, restores the weights, identifies the held-out test series from the fold name, and runs tiled inference over every frame in that series.

Output is printed to the terminal:

------------------------------------------------------------

Inference

Run a trained model on a directory of images using the threshold selected on the validation set for that same fold. The easiest place to find it is run_summary.json → best_validation_thresholds.

ciproseg-infer \
  --ckpt runs/.../fold_01_test_seriesA/best.pt \
  --input path/to/images/seriesA/ \
  --output predictions/seriesA/ \
  --threshold 0.45

For each input image (say frame_001.tif), the following files are written:

File Description
frame_001_prob.npy Original float32 probability map with values in [0, 1]. This is the authoritative numerical probability output and can be re-thresholded later without rerunning the U-Net.
frame_001_prob.png 16-bit visualisation of the probability map. Probabilities in [0, 1] are mapped to integer intensities in [0, 65535].
frame_001_binary.png Binary mask produced using the chosen threshold. Pixels are 0 for background and 255 for foreground.
frame_001_pred_overlay.png Input image with predicted boundaries drawn in green
Which output should downstream analysis use?
Connected Components, watershed, cell counting, and morphology analysis should normally start from *_binary.png. Use *_prob.npy when you want to apply a different threshold later without rerunning the neural network. The *_prob.png file is primarily a convenient visual representation of the probability map.

When you also provide ground-truth masks with --masks, two additional files are generated per image:

File Description
frame_001_gt_overlay.png Input image with ground-truth boundaries in cyan
frame_001_diff.png Colour-coded difference map: TP green, FP red, FN blue, TN dark

Full example

ciproseg-infer \
  --ckpt .../best.pt \
  --input path/to/images/seriesA/ \
  --masks path/to/masks/seriesA/ \
  --output predictions/seriesA/ \
  --threshold 0.45 \
  --patch 512 \
  --stride 256

Other options: --cpu, --device cuda:1, --verbose (enables DEBUG-level per-file logging).

Web GUI

CiproSeg ships with an optional browser-based interface for users who prefer not to work from the command line. The GUI wraps the same CLI commands described above; it does not replace them.

ciproseg-gui

This opens a browser tab at http://127.0.0.1:7860 with pages for training configuration, live training monitoring, evaluation, inference with side-by-side image viewing, results browsing, and cross-fold comparison.

On launch, the GUI loads configs/experiment.yaml (if present) and populates the form fields automatically. All training, evaluation, and inference parameters can be edited directly in the browser without touching any YAML files.

Options

Flag Purpose
--port 8080 Use a custom port instead of the default 7860
--no-browser Start the server without auto-opening the browser
--host 0.0.0.0 Bind to all interfaces for remote access (e.g. from another machine on the network)

If a port is already in use (say, another GUI instance is running), the server automatically finds the next available port. Multiple instances can run side by side without manual port management.

ciproseg-gui --port 8080            # custom port
ciproseg-gui --no-browser           # skip auto-opening the browser
ciproseg-gui --host 0.0.0.0        # bind to all interfaces (remote access)
ℹ️ Dependencies
The GUI requires the [gui] optional dependencies (fastapi, uvicorn). If these are not installed, the core CLI tools remain fully functional. See Installation for setup instructions.

Configuration Reference

The experiment config (configs/experiment.yaml) is the single source of truth for a CiproSeg training run. All sections are described below.

dataset

Field Description
name Dataset loader identifier. Currently only ciproseg_ecoli is supported.
root Absolute path to the dataset directory containing image/mask pairs.
train_frac Fraction of non-test frames used for training within each fold. Default: 0.8.
patch Crop size in pixels for training patches. Must be divisible by 16 for unet4 or by 4 for unet2.
stride Stride for tiled inference on validation and test frames.

model

Field Description
name Architecture variant. unet2 uses 2 levels; unet4 uses 4 levels (recommended).
in_channels Number of input channels. Set to 1 for grayscale microscopy.
out_channels Number of output channels. Set to 1 for binary segmentation.
base_channels Feature maps in the first encoder block. Doubles at each subsequent level.

trainer

Field Description
epochs Training epochs per fold.
batch_size Patches per gradient step.
num_workers DataLoader workers. Set to 0 for debugging.
seed Base random seed. Each fold derives its seed as seed + 1000 * fold_id.
target_patches_per_epoch Controls how many random crops are sampled per epoch.
deterministic Enables PyTorch deterministic mode. Slower but more reproducible.
benchmark Enables cudnn.benchmark. Faster on fixed input sizes.
cpu Force CPU training even when a GPU is available.
output_dir Root directory for outputs. Each run creates a timestamped subdirectory.
amp Enable automatic mixed-precision training when supported.
early_stop_patience Number of validation checks without improvement allowed before early stopping.
test_tta Enable test-time augmentation for final full-image evaluation.
compute_object_metrics Also compute object-level counts and matching metrics during final test evaluation.

validation

Threshold handling is deliberately separated from the trainer settings. The configuration used by the current workflow is:

validation:
  checkpoint_threshold: 0.5
  threshold_sweep: true
  sweeping_thresholds: [0.30, 0.35, 0.40, 0.45, 0.50, 0.55, 0.60]
Field Description
checkpoint_threshold Threshold used during periodic validation to compute binary validation metrics and decide whether the current checkpoint becomes best.pt. Default convention: 0.5.
threshold_sweep When true, the best checkpoint is re-evaluated on the validation set after training using every candidate threshold. When false, no sweep is performed and checkpoint_threshold is used.
sweeping_thresholds List of candidate probability thresholds. The list can contain any number of values in the open interval (0, 1). The threshold with the highest mean validation Dice is selected.

optim

Field Description
name Optimizer. Supported: adam, adamw (default), sgd.
lr Initial learning rate.
weight_decay L2 regularisation. Bias and normalisation parameters are automatically excluded.

sched

Field Description
name Scheduler. none keeps the LR constant. Also supports cosine, step, and onecycle.
tmax (Cosine only) Epochs over which the LR anneals from lr to zero.

logger

Field Description
name Logger identifier used in log output.
level Logging verbosity: DEBUG, INFO, WARNING, ERROR.

SLURM / HPC

Job scripts for GPU and CPU-only partitions are provided in scripts/:

sbatch scripts/slurm_gpu.sh    # GPU partition
sbatch scripts/slurm_cpu.sh    # CPU-only partition

Both scripts auto-detect the project root relative to the submission directory. Thread counts for CPU-bound operations (OpenMP, MKL, OpenBLAS) are set from SLURM_CPUS_PER_TASK automatically.

Training output goes to train.log inside the timestamped run directory. SLURM's own slurm-<jobid>.out captures driver errors, OOM kills, and other system-level messages.

💡 Tip
Submit from the project root or the scripts/ directory. The scripts walk up one level if needed to find configs/experiment.yaml.

How It Works

Engine

The Engine orchestrates runs but contains no task logic of its own. It lazily builds the Trainer on first access, so evaluation-only workflows never touch training code. On fit(), it delegates to the Trainer and fires lifecycle hooks at the end.

Trainer

The Trainer owns the full LOSO loop. It builds the dataset index, creates N folds (one per series), and trains each fold sequentially. Within a fold, periodic validation uses validation.checkpoint_threshold to compute the Dice score used for checkpoint selection. After training finishes, the Trainer reloads best.pt, sweeps the configured candidate thresholds on the validation set, and chooses the threshold with the highest mean validation Dice. That fixed threshold is then applied once to the held-out test series. The test data do not participate in threshold selection.

Each fold gets a deterministic seed derived from the base seed (seed + 1000 * fold_id), so results are reproducible even when folds run in sequence.

Evaluator

The evaluate_checkpoint() function is fully standalone. It loads a checkpoint, rebuilds the model from the config stored inside it, identifies the held-out test series from the fold name, and runs tiled inference. No config file needed.

Checkpointer

Handles atomic file writes using a temporary file followed by os.replace(), both for fold-level checkpoints and the run summary. JSON sidecars carry metadata without requiring torch.load to browse results.

Tiled inference

Handles images larger than the patch size by splitting them into overlapping tiles, running each through the model, and averaging predictions in overlap regions. Tile positions are computed deterministically to ensure full coverage. Padding is applied automatically when an image or tile is smaller than the patch size.

Hook system

A lightweight lifecycle hook system fans out calls at key points: train start/end, fold start/end, epoch start/end, batch start/end, and eval start/end. The built-in ProgressBar hook handles all console and file logging. You can add custom hooks by subclassing Hook and overriding the methods you need.

Models

CiproSeg ships with two U-Net variants, both registered through a decorator-based model registry. Having multiple architectures lets you trade off between segmentation accuracy and computational efficiency choose the right model for your data scale, hardware, and experimental goals.

🎯

Right-Sized Architecture

Match model capacity to your dataset. Large datasets benefit from UNet4's depth; small datasets converge faster with UNet2's compact design.

⚡

Rapid Prototyping

Use UNet2 for quick debug runs and hyperparameter sweeps, then switch to UNet4 for production quality with a single config change.

🧠

Hardware Flexibility

UNet2 trains on laptops and CPU-only machines. UNet4 leverages GPU memory for higher-capacity encoding across 4 resolution levels.

📊

Baseline Comparison

Compare a lightweight vs. deep architecture on the same LOSO folds quantify exactly how much additional depth improves your segmentation metrics.

🏗️

UNet4: Full-Depth Architecture

Recommended

The standard 4-level encoder-decoder U-Net is CiproSeg's default model. Four downsampling stages progressively compress the spatial resolution through max pooling, while doubling the feature channels at each level. A bottleneck block at the deepest level captures the most abstract contextual features before the decoder reconstructs the segmentation map through four upsampling stages with transposed convolutions and skip connections.

Each block applies the DoubleConv pattern (Conv2d → BatchNorm → ReLU, repeated twice) to ensure stable gradient flow and rich feature extraction at every resolution. Skip connections concatenate encoder features with decoder features at each level, preserving fine spatial details that would otherwise be lost during downsampling.

UNet2: Lightweight Architecture

Fast

The 2-level U-Net strips the architecture down to two encoder-decoder stages with a compact bottleneck. It uses the same DoubleConv building blocks as UNet4 but defaults to base_channels=32 instead of 64, resulting in an order-of-magnitude fewer parameters. The shallower network trains significantly faster with lower memory requirements.

Despite its compact design, UNet2 captures sufficient spatial context for many microscopy segmentation tasks, especially when cells are well-separated or the training set is small. It serves as an excellent baseline for ablation studies and is ideal for iterating on augmentation strategies, sampling hyperparameters, or debugging data pipeline issues before committing to a full UNet4 training run.

Model registry

Models are registered with the @register_model decorator:

from ciproseg.models.registry import register_model

@register_model("my_model")
def build_my_model(**kwargs):
    return MyModel(**kwargs)

The registry is populated at import time. The models/__init__.py file eagerly imports all built-in model modules to ensure their decorators fire before any code tries to look up a model by name.

Data Pipeline

Index building

build_index() scans the dataset root, matches image/mask filenames, and returns a dictionary mapping series names to lists of FrameItem dataclass instances. It validates that every image has a corresponding mask and raises a clear error on mismatch.

Fold construction

make_loso_folds() produces one fold per series. For each fold, build_fold_splits() splits the remaining series by temporal order: the first 80% of frames (by default) become training data, the last 20% become validation data. This temporal split avoids information leakage from future frames into training.

Patch sampling

Training uses RandomCropSegDataset, which draws random crops from full-resolution frames on the fly. The sampling strategy is a weighted mixture of three modes:

Mode Default weight Behaviour
Foreground 60% Centres patches on foreground pixels
Boundary 30% Centres patches on morphological boundaries
Random 10% Uniform random placement

The number of crops per frame per epoch is derived from target_patches_per_epoch, clamped between configurable bounds.

Augmentation

Image/mask pairs are augmented consistently with horizontal flip, vertical flip, small rotations (up to 15 degrees), brightness/contrast jitter, and Gaussian noise. All operations use OpenCV for speed.

Metrics

CiproSeg reports four segmentation metrics, all computed from the confusion matrix after thresholding the probability map:

Metric Formula
Dice 2TP / (2TP + FP + FN)
IoU (Jaccard) TP / (TP + FP + FN)
Precision TP / (TP + FP)
Recall TP / (TP + FN)

A small epsilon (1e-8) is added to both numerator and denominator to avoid division by zero on empty frames. Metrics are computed per frame and then averaged across all frames in the series.

Two implementations exist: a PyTorch tensor version (used during training for quick validation) and a NumPy version (used during full-image tiled evaluation). Both produce identical results.

When validation threshold sweeping is enabled, all four metrics are reported for every candidate threshold, but the selection criterion is fixed to mean validation Dice. Precision, recall, and IoU are reported for interpretation; they do not independently choose the threshold.

Extending CiproSeg

Adding a new model

Create a new file under src/ciproseg/models/, define your architecture, and register it:

# src/ciproseg/models/my_arch.py

import torch.nn as nn
from .registry import register_model

class MyArch(nn.Module):
    def __init__(self, in_channels=1, out_channels=1, **kwargs):
        super().__init__()
        # ... build layers ...

    def forward(self, x):
        # ... return raw logits (no sigmoid) ...
        return x

@register_model("my_arch")
def build_my_arch(**kwargs):
    return MyArch(**kwargs)

Then import the module in models/__init__.py:

from . import my_arch as _my_arch

Set model.name: my_arch in your config and train as usual.

⚠️ Important
The @register_model decorator only fires when the module is imported. If you skip the import in __init__.py, the model will not be found by the registry at inference time.

Adding a new dataset

Create a dataset class under src/ciproseg/data/datasets/ following the same pattern as ciproseg_ecoli.py: a build_index() function that returns a dict of series to frame lists, and a make_loso_folds() function. Wire it into build_datamodule() by checking the dataset.name field in the config.

Adding custom hooks

Subclass Hook from ciproseg.core.hooks and override the lifecycle methods you need. Then pass your hook to the Engine or add it to the HookList.

Testing

pytest tests/

The test suite covers model forward passes, dataset indexing and fold splitting, loss computation and gradients, checkpoint saving and loading, and training orchestration (via monkeypatched stubs). Tests use temporary directories and synthetic data, so no GPU or real dataset is needed.

For static analysis:

ruff check src/
mypy src/

Design Decisions

Single GPU only

No DDP, no torchrun, no DeepSpeed. The codebase includes basic distributed scaffolding (device resolution, rank checks, dist helpers) for possible future use, but the training loop is strictly single-GPU. This keeps the code simple, the experiments reproducible, and the debugging straightforward.

No mid-fold resume

Checkpoints are saved per fold, but training always restarts from fold 1. LOSO folds are fast enough on a single GPU that this is rarely a practical issue.

Self-contained checkpoints

Every .pt file stores the full config alongside weights. This means you can evaluate or run inference on a checkpoint months later without needing the original config file.

Timestamp-based run directories

Each training run gets a unique directory based on the model name and current timestamp. Nothing is ever overwritten.

Temporal validation split

Within each fold, training and validation frames are split by temporal order (first 80% / last 20%) rather than randomly. This avoids information leakage from temporally adjacent frames.

Validation frequency

Validation metrics are computed every 10 epochs rather than every epoch. This reduces overhead for large datasets while still providing enough resolution for checkpoint selection. The final epoch always triggers a validation pass.

Separate checkpoint and final thresholds

validation.checkpoint_threshold provides a stable threshold for comparing checkpoints during training. The final binarisation threshold is selected only after training by sweeping the configured candidates on the validation set. Keeping these roles separate makes the procedure explicit and prevents the held-out test series from influencing threshold choice.

Decoupled GUI

The web interface is entirely optional and calls the CLI tools as subprocesses. If the GUI is not installed, corrupted, or otherwise unavailable, all core functionality works from the command line exactly as documented above.
